# 8. Cross-cutting Concepts

## 8.1 Authorization Concept

There are two levels of roles:

- **System-wide:** *system administrator* or *normal user*. Any user can create a team.
- **Per team:** **Admin**, **Editor**, **Reader**. These apply across the Teams, Folders, and Situations modules (chapter 5). The creator of a team becomes its Admin. Members whose join request is accepted start as Reader.
- **Personal area:** only its owner can read and write it.

**System administrators** manage users and teams, but have **no access to situations or folders** (neither personal nor team):

| Action | System administrator |
|---|---|
| List users, block/unblock, delete a user | ✅ |
| Grant/revoke system administrator | ✅ (the last system administrator can't lose the role, block or delete themselves) |
| List teams, delete a team | ✅ |
| Manage a team's members and roles (also accept/reject join requests) | ✅ |
| View or change situations and folders | ❌ |

A blocked user can't log in or call the API; their content and memberships stay.

**Team permission matrix (confirmed):**

| Action | Admin | Editor | Reader |
|---|---|---|---|
| View team's boards/folders | ✅ | ✅ | ✅ |
| Create/edit/delete a board | ✅ | ✅ | ❌ |
| Create/rename/delete a folder | ✅ | ✅ | ❌ |
| Accept/reject join requests | ✅ | ❌ | ❌ |
| Manage team members/roles (remove members, change roles, own role included²) | ✅ | ❌ | ❌ |
| See the member list | ✅ | ✅ | ✅ |
| Leave the team | ✅¹ | ✅ | ✅ |
| Delete the team | ✅ | ❌ | ❌ |

Not in the matrix (confirmed product decision, roadmap step 7): **rename the team, set/replace/remove its logo** — the team's Admins and system administrators (the system-administrator part is built with system administration, roadmap step 9; until then Admins only). Seeing a team's **name and logo** (in the overview and on its page) needs only a login, no membership; its **code and link** only members see (confirmed product decision; the API leaves the code out for non-members).

¹ Except the team's last Admin, who has to delete the team instead.
² As long as the team keeps at least one Admin.

Enforcement point: the backend. The Teams module owns the role check (`ITeamAuthorization`, ch. 8.17); Situations and Folders ask the Areas module, which delegates to Teams or Users (ch. 5.2), rather than duplicating authorization logic. The frontend only hides what isn't allowed.

**Team content (implemented, roadmap Phase 2 step 8):** "View" = list folders and situations, open a situation (also play it back and export it); "Create/edit/delete" = first save, later saves, Save as copy, move between folders, delete situations; create, rename and delete folders. Only a **membership** counts: a system administrator without one has no access (also not to read); a system administrator who is a member has that member's rights (open question in the roadmap). The role is read from the database for every request, so a demotion, a removal or leaving takes effect with the next request. Answers for content the user may not touch (ch. 8.15): an area they can't read (non-members) — its lists `403 forbidden`, a single folder or situation in it `404` (no hint that it exists); readable but not writable (Readers) — `403 forbidden`. The API tells the UI what is allowed with `canWrite` on every folder and situation. The editor opens a situation with `canWrite: false` **read-only** (conservative choice, open question in the roadmap).

## 8.2 API Error Handling

Confirmed: consistent error responses using [RFC 7807 Problem Details](https://www.rfc-editor.org/rfc/rfc7807) (`application/problem+json`), which ASP.NET Core supports natively. Validation errors list the invalid fields (`errors`); domain errors (e.g. duplicate title, save conflict, last Admin) have their own `type` URI so the frontend can react to them.

Example shape:

```json
{
  "type": "https://tacticalboard/errors/forbidden",
  "title": "Forbidden",
  "status": 403,
  "detail": "Role 'Reader' cannot edit boards in this team."
}
```

Conventions (implemented):

- Every problem `type` is `https://tacticalboard/errors/{code}`, the code in kebab-case. The URI is an identifier, not a page to fetch.
- **Domain errors** derive from `DomainException` (SharedKernel) with a transport-neutral kind and their own code, e.g. `duplicate-title`. The kind decides the status: Validation → 400, Forbidden → 403, NotFound → 404, Conflict → 409, PreconditionFailed → 412.
- **Framework errors** get a code from their status's reason phrase: `bad-request`, `not-found`, `method-not-allowed`, … Validation errors (with `errors`) are `validation-failed`; unexpected exceptions are `500` `internal-error` without any internal details.
- Every problem has `status`, `instance` (the request path) and `traceId`.
- A domain error may add its own extension members (`DomainException.Details`, camelCase), e.g. `currentRevision` of a save conflict.
- Login-related types: `unauthorized` (401, no or no longer valid session), `forbidden` (403), `invalid-antiforgery-token` (400, ch. 8.13).
- Saved situations (8.15): `situation-not-found` (404), `forbidden` (403), `duplicate-title` (409, with `existingTitle`), `save-conflict` (412, with `currentRevision`), `precondition-required` (428, a save without `If-Match`), `field-type-changed` / `sport-changed` (400), `validation-failed` (400, `errors` keyed `document.<path>` / `origin`).
- Team areas (8.15): `team-not-found` (404, `/api/teams/{team}/folders|situations` for a team that doesn't exist (any more) or a malformed key), `forbidden` (403, a non-member listing or creating, a Reader writing).
- Folders (8.15): `folder-not-found` (404; also for a move or first save into a folder that is gone or lies in another area), `forbidden` (403), `duplicate-folder-name` (409, with `existingName`), `folder-not-empty` (409, deleting a folder that still contains situations), `validation-failed` (400, `errors.name`).
- Users (8.13, 8.18): `validation-failed` (400) with `errors.displayName` or `errors.language`.
- Teams (8.17): `team-not-found` (404; also for a malformed code or id), `team-logo-not-found` (404), `forbidden` (403, changing a team or its members without being its Admin, seeing the members without being one), `duplicate-team-name` (409, with `existingName`), `last-team-admin` (409, the change would leave the team without an Admin), `team-member-not-found` (404), `join-request-not-found` (404, no such pending request — also one decided meanwhile), `join-request-pending` (409, the user's request is pending already), `already-team-member` (409, a member asks to join), `validation-failed` with `errors.role` (`required`, `invalid-value`) for a role change, `validation-failed` (400, `errors.name` / `errors.logo`, `errors.search` / `offset` / `limit` of the overview), `payload-too-large` (413, an upload request larger than the server reads; ASP.NET Core's reason phrase "Content Too Large" gives the code).

**Stable codes, worded by the client** (confirmed product decision, roadmap Phase 2 step 5; ch. 8.18): the `type` is the stable code of a problem; the English `title` and `detail` are for logs and API consumers only — the frontend never shows them, it words the code in the UI language and falls back to a generic message for codes it doesn't know. Validation problems carry, next to the ASP.NET Core standard `errors` (English messages per field), the extension member **`fieldErrors`** with the same keys in the same order: per field a list of `{ "code": "…", …values }`:

```json
{
  "type": "https://tacticalboard/errors/validation-failed",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": { "name": ["expected at most 100 characters"] },
  "fieldErrors": { "name": [{ "code": "too-long", "maxLength": 100 }] }
}
```

Field error codes: `required` (empty or missing), `too-long` (`maxLength`), `control-characters`, `invalid-value` (e.g. an unknown `origin`), `unsupported-language` (not a language tag); for logo uploads (8.17): `file-too-large` (`maxBytes`), `unsupported-image` (no readable PNG, JPEG or WebP), `image-too-large` (`maxMegapixels`); for situation documents (keys `document.<path>`, the validator's issues, 8.3/8.15): `expected-object`, `expected-value` (`expected`), `expected-positive-integer`, `expected-current-version` (`version`), `expected-supported-sport`, `expected-field-type`, `expected-array`, `expected-frame`, `duplicate-id` (`id`), `expected-element-type`, `expected-label`, `expected-string`, `expected-non-empty-string`, `expected-finite-number`, `expected-point`, `expected-timestamp`. A new rule gets a new code; an existing code never changes its meaning.

Implementation: `backend/src/TacticalBoard.SharedKernel/Errors/`, `backend/src/TacticalBoard.SharedKernel/Validation/` (`FieldError`: code, English message, values; `FieldErrors`: the per-field collection that yields `errors` and `fieldErrors`), `backend/src/TacticalBoard.Api/ErrorHandling/` (`ProblemTypes`, `DomainErrorStatusCodes`, `DomainExceptionHandler`, `ProblemDetailsEnricher`); the modules' endpoints build validation problems with `TypedResults.ValidationProblem(errors.Messages(), extensions: errors.Extensions())`. Frontend: `ApiError.code` / `ApiError.fieldErrorCodes()` (`frontend/src/lib/api/ApiClient.ts`) and `ProblemText` (`frontend/src/lib/i18n/`, ch. 8.18).

## 8.3 Situation File Format

Situations are exported and imported as JSON files named `<slug-of-title>.situation.json` (`situation.json` if the title yields no usable characters), pretty-printed with a 2-space indent.

**Format version 3** (current):

```json
{
  "format": "tacticalboard.situation",
  "formatVersion": 3,
  "situation": {
    "id": "…",
    "title": "Powerplay vs. 2-3-1",
    "description": "Markdown source",
    "sport": "floorball",
    "fieldType": "full",
    "createdAt": "2026-03-01T10:00:00.000Z",
    "updatedAt": "2026-03-02T12:30:00.000Z",
    "frames": [
      {
        "id": "…",
        "description": "Markdown source",
        "elements": [
          { "id": "…", "type": "Pass", "color": "oklch(15% 0 0)", "start": { "x": 1200, "y": 300 }, "end": { "x": 1600, "y": 500 }, "bends": [{ "x": 1450, "y": 300 }] },
          { "id": "…", "type": "Player", "color": "oklch(62% 0.16 230)", "x": 1200, "y": 300, "label": "C" }
        ]
      }
    ]
  }
}
```

- `format` identifies the file as a TacticalBoard situation; `formatVersion` is a positive integer.
- `sport`: currently only `floorball`. `fieldType`: `full` or `half`; fixed when the situation is created.
- `title` may be empty (the UI then shows the default title of the UI language, e.g. "Untitled Situation", ch. 8.18). Descriptions are Markdown source.
- `createdAt`/`updatedAt` are ISO 8601 timestamps.
- There is at least one frame. Frame IDs are unique within the situation; element IDs are unique within a frame, and the same element ID in different frames denotes the same element.
- Element `type`: the **point elements** `Player`, `Ball`, `Rectangle`, `Triangle`, `Circle` (with `x`, `y`, `label`) and the **arrows** `Pass`, `Run`, `Shot` (with `start`, `end`, `bends`; no `x`/`y`/`label`). The validator checks the properties of the element's kind; extra properties (also `x`/`y`/`label` on an arrow) are ignored. There are no rules on how many of each a frame may contain. The order of `elements` is the z-order (bottom first); arrows are nevertheless always drawn below point elements.
- **Coordinates** (`x`, `y`, and every point of an arrow) are always in full-field scene units of the sport (floorball: 2000 × 1000, origin top-left), also for half-field situations. A half-field situation uses the right half, `x ∈ [1000, 2000]` (see 8.6).
- Arrow `start`, `end`: `{ "x": …, "y": … }` with finite numbers. `bends`: the **bend points** the curve passes through, in order from start to end; `[]` for a straight arrow; any number. Start and end may coincide (the app itself never creates such an arrow, see 8.10).
- Element `label` (point elements only): the **position label**, `""` (no label) or 1–2 characters, each a letter or a digit (e.g. `C`, `LV`, `10`). Stored per element **per frame**, like the color; duplicates within a frame are allowed. Every element type carries it, but only players show it: changing a player to another type hides the label, changing it back shows it again. The UI upper-cases typed letters; the importer also accepts lower case and keeps it as is.
- Unknown extra properties are ignored on import.

**Format history:**

| Version | Change | Migration from the previous version |
|---|---|---|
| 1 | Initial situation format | – |
| 2 | Elements get `label` | `MigrationV1ToV2`: every element gets `"label": ""` (a `label` property in a v1 file was an ignored extra property and is replaced) |
| 3 | Arrow elements `Pass`, `Run`, `Shot` with `start`, `end`, `bends` | `MigrationV2ToV3`: none needed — v2 files contain no arrows (the types were unknown) and point elements are unchanged; the content passes through, only `formatVersion` changes |

**Versioning and migration policy:** every change to the file format bumps `formatVersion` and comes with a migration from the previous version, so files exported by older app versions keep importing. Import runs parse → migrate (chained, one version step at a time) → validate → map to the domain model. Files with a newer version than the app supports are rejected with a request to update the app. The validator reports all problems at once, with paths such as `situation.frames[0].elements[2].x: expected finite number`.

**Legacy format:** the pre-v1 export (a top-level JSON array of elements) is not supported and is rejected with "This file uses an old format that is no longer supported".

**Import creates a new situation:** the imported situation gets a fresh situation ID, and `createdAt` and `updatedAt` are both set to the import time; frame and element IDs are kept. It replaces the content of the editor (after "Discard changes?" if there are unsaved changes, see 8.7). A file that fails to import changes nothing and is not followed by that question.

Implementation: `frontend/src/lib/model/serialization/` (`SituationSerializer` facade, `SituationFileMigrator` with one `Migration` per version step: `MigrationV1ToV2`, `MigrationV2ToV3`; `SituationFileValidator`, `SituationMapper`); label rules and the predefined positions per sport in `frontend/src/lib/model/positions/PositionCatalog.ts`. Test fixtures for every format version live in `__fixtures__/`, so older files keep being tested.

## 8.4 Editing via commands (undo/redo)

Every change to a **frame's content** (its elements and its description) goes **`SituationEditor` → command → the active frame's `CommandHistory`**. UI components never construct commands or change the model themselves; they call the editor's public methods (`addElement`, `moveElement`, `addArrow`, `reshapeArrow`, `moveArrow`, `addBend`, `removeBend`, `straightenArrow`, `changeFrameDescription`, `undo`, `redo`, …).

**Situation-level changes** take a second, non-undoable path (`SituationEditor.updateSituation`): adding, deleting, and reordering frames (`addFrame`, `deleteFrame`, `moveFrame`) and the situation's title and description (`changeTitle`, `changeDescription`). Like commands, they refresh `updatedAt` and mark the situation as unsaved (8.7), but they are not recorded in any history; inside the text fields the browser's own undo works while typing. See 8.9 for the frame operations.

- **Commands** work on the immutable model: `execute(frame)` / `undo(frame)` return a new frame and address elements by id, never by reference or index. A command records what it needs to revert itself (e.g. the removed element and its z-order index, a move's start position). Commands that would change nothing (same position/color/type/shape, unknown id) are not recorded. A type change is only possible within the element's family (point types among each other, arrow types among each other); `ChangeElementTypeCommand` refuses anything else. All arrow shape changes — dragging its start, end or a bend, adding/removing bends, straightening, moving the whole arrow — are one command type, `ReshapeArrowCommand` (old and new `ArrowGeometry`). Several commands can be grouped into one undo step with `CompositeCommand`.
- **One history per frame**, keyed by frame id: undo/redo always act on the active frame's history. Switching frames is not an undo step. A new frame starts with an empty history; a deleted frame's history is dropped.
- **Limit:** 200 steps per frame; the oldest steps are dropped. Histories live in memory only and do not survive a page reload.
- **Loading/importing or creating a situation is not undoable** and clears all histories.
- **Edit sessions:** until the history is sealed (`SituationEditor.endGesture()`, called at the end of a drag, when a text field loses focus or Enter is pressed in it, and when the popover closes), a new command may merge into the previous one (`Command.mergeWith`). So consecutive moves of one element during a gesture, all reshapes of one arrow during a handle or body drag, or all keystrokes of one text-field focus (e.g. the free-text position label or the frame description), become a single undo step. Picking a position chip is one step of its own; so are adding a bend, removing a bend and straightening (the editor seals before and after them). Undo, redo, and switching frames also seal.
- **Undoable vs. not undoable:**

  | Undoable (in the active frame's history) | Not undoable |
  |---|---|
  | Place, move, delete an element; change its type, color, position label | Add, delete, reorder frames |
  | Draw an arrow; move it; drag its start, end or a bend; add or remove a bend; straighten it | Arrow drawing in progress (start point, preview) |
  | Change the frame description (one step per focus of the field) | Change the situation's title or description |
  | | Switch frames, selection, tool changes; create/load/import a situation |

  After undo, nothing is selected automatically.
- **Feedback:** undo/redo is shown only via the enabled state of the Undo/Redo buttons; what was undone/redone is logged to the debug notification log, not shown as user-facing UI. Undo/redo with nothing to undo/redo (e.g. via the keyboard shortcut) does nothing and logs nothing.
- **Shortcuts:** Ctrl/Cmd+Z undo; Ctrl/Cmd+Shift+Z and Ctrl+Y redo. Ignored while typing in text fields, during IME composition, with Alt held, and while an element is being dragged.

Implementation: `frontend/src/lib/history/` (generic: `Command`, `CommandHistory`, `CompositeCommand`, `FrameHistories`, `UndoRedoShortcuts`) and `frontend/src/lib/commands/` (one class per frame command).

## 8.5 Touch interaction concept

The board editor is fully usable by touch on phones (portrait and landscape) and tablets, and with mouse and keyboard on desktop. Touch, mouse, and pen share one interaction model; there is no separate "mobile mode".

**Gestures** (all devices; drawing and editing arrows: see 8.10):

| Gesture | Effect |
|---|---|
| Tap/click on an element | Selects it **and** opens the edit popover (type within its family, color, for players the position label, for arrows the bend actions; Delete). Same with any tool active: a tap on an element never places a new element on top of it (with an arrow tool only while no arrow start point is pending, see 8.10). |
| Tap/click on the empty field, point placement tool active | Places an element there (Player in the selected player color, everything else neutral). The tool stays active; the new element is **not** selected. Clears the selection. |
| Tap/click on the empty field, Move tool | Clears the selection and closes the popover. |
| Drag an element | Moves it (an arrow as a whole, keeping its shape); one drag = one undo step. The popover closes while dragging, the selection stays. Elements can't be dragged out of the visible area (the field, or the visible half — see 8.6). Not with an arrow tool active: a press then starts an arrow (8.10). |
| Right-click / long-press on an element | Same as a tap. |
| Delete button in the popover | Deletes the element. |
| Close button in the popover | Closes the popover **and** clears the selection (like Escape). |
| Desktop only: Shift+click, Delete/Backspace, Escape | Shift+click deletes the clicked element; Delete/Backspace deletes the selected element; Escape drops an arrow being drawn, clears the selection and closes the popover. Ignored while typing in a text field (e.g. the position label field), so Delete/Backspace there edits the text and never deletes the element. |

A press only turns into a drag after the pointer has moved 6 CSS px (Konva `dragDistance`), so finger jitter doesn't move elements. Taps use Konva's `pointerclick`, which fires for mouse, touch, and pen alike and not after a drag.

**Popover lifetime:** the popover stays open when the tool changes and when the device is rotated or the window resized. Whenever the stage geometry changes (refit, window resize), `BoardCanvas` asks `BoardInteractionController.relocatePopover` to re-anchor it at the selected element's new on-screen position, so it never floats at a stale place. It closes on a tap on the empty field, Escape, Close, undo/redo, the start of a drag (also of an arrow handle), deleting the element, and "Edit shape" (arrows; keeps the selection, see 8.10).

**Popover placement** (`PopoverPlacement`, larger screens): below the anchor (the element's on-screen bounds, for an arrow the bounds of its curve), horizontally centered; above it when there is no room below; to its right or left, vertically centered, when it fits neither below nor above (typical for a large arrow) — so it doesn't cover the element. Only when it fits nowhere it may overlap the element. On phones it is a bottom sheet instead.

**Position labels on the board:** a player's label is drawn centered on it in black or white, whichever contrasts more with the fill (`LabelContrast`, WCAG luminance; oklch, hex and rgb fills understood, others fall back to black). The text node does not listen to pointer events, so taps and drags hit the player beneath; it follows the player while dragged and is counter-rotated against the stage, so it stays upright on the rotated half field.

**Hit-area rule:** elements are drawn in scene units and scale with the field, so they look the same (proportional) on every device. Their invisible hit area is a solid circle of radius `max(visual radius, 22 CSS px / scale)`, i.e. at least 44 CSS px across on screen. An arrow's hit area is its curve stroked 44 CSS px wide; the handles of the selected arrow have hit circles of 44 CSS px. Where hit areas of nearby elements overlap, the topmost element wins; a tap inside an element's enlarged hit area selects it rather than placing a new element.

**Field fitting:** the visible part of the field is scaled uniformly as large as fits and centered, re-fitted whenever its container changes size. The full field (2000 × 1000 scene units) is scaled by `min(available width / 2000, available height / 1000)` and never rotated — on a portrait phone it stays horizontal and becomes small. The half field is shown in portrait (see 8.6).

**No pinch-zoom (MVP):** the board area disables browser touch gestures (`touch-action: none`), so pinching neither zooms the page nor the board. See [known limitations](../known-limitations.md).

**Layout:** desktop (≥ 1024 px) has a side tool panel on the left and the details panel (8.9) on the right; tablets (600–1023 px) keep the side tool panel with tighter spacing and, in portrait (≥ 500 px tall), show the details panel below the board so the field keeps the width; portrait phones (≤ 599 px wide) get a compact header with icon-only buttons and the tools as a horizontally scrollable bottom bar; landscape phones (≤ 499 px tall) get a compact header and a narrow left tool rail. On phones the details panel collapses to a "Details" bar above the board (collapsed by default) and the edit popover becomes a bottom sheet. The playback controls (8.11) and the frame strip (8.9) sit directly below the board on every layout (on landscape phones at least 780 px wide side by side, to save height); its action buttons become icon-only when the strip is narrower than 720 px (CSS container query). Interactive controls are at least 44 × 44 CSS px; icon-only buttons keep their text as accessible name. Safe-area insets (notches, home indicator) are respected.

Implementation: `frontend/src/lib/board/` (`BoardViewport`, `BoardInteractionController`, `ArrowGestures`, `ArrowHandle`, `Selection`, `ToolState`, `PopoverState`, `konvaSetup`), `frontend/src/lib/components/board/BoardCanvas.svelte` (translates Konva events into gestures), `frontend/src/lib/components/board/popover/`.

## 8.6 Field viewport and coordinate convention

**Scene coordinates:** the model stores every position in full-field scene units of the sport, origin top-left, x to the right, y down (`FieldDimensions`, floorball 2000 × 1000). This holds for half-field situations too, so a half-field situation's data is unambiguous and the drawing code is the same for both field types.

**Half-field convention:** a half-field situation always uses the **right half**, `x ∈ [width / 2, width]` (floorball: `x ∈ [1000, 2000]`, `y ∈ [0, 1000]`). The user never chooses a half. Elements outside the visible half (e.g. from a hand-edited or full-field-derived file) stay in the data unchanged; they are simply not visible.

**Viewport** (`BoardViewport`, one per sport + field type):

| | Visible rect (scene units) | Stage rotation | Orientation on screen |
|---|---|---|---|
| Full field | `(0, 0, 2000, 1000)` | 0° | landscape, never rotated |
| Half field | `(1000, 0, 1000, 1000)` | 90° clockwise | portrait, the half's goal (x = 2000) at the **bottom**, the center line at the top |

- The visible rect is scaled uniformly to fit the container (`fit`); for the half field the rect's width and height swap on screen. The Konva stage gets flat `scaleX`/`scaleY`, `rotation`, `x`, `y` props so that the visible rect fills the stage exactly. The whole field is still drawn; the stage's size crops everything outside the visible rect.
- Mapping (stage CSS px relative to the stage container ↔ scene): `stage = (x₀, y₀) + R(θ)·scale·scene`, with `R(90°)·(x, y) = (−y, x)`. `BoardViewport.sceneToStage`/`stageToScene` implement it; taps are converted with `stageToScene`, popover anchors with `sceneToStage` (round elements, so the anchor rect stays axis-aligned). Konva's own transform for dragging uses the same stage props; tests check that both agree.
- **Clamping:** placing and dragging clamp to the visible rect — the whole field for full-field situations, the visible half for half-field ones — so new and moved elements are always visible.

Implementation: `frontend/src/lib/model/FieldDimensions.ts`, `frontend/src/lib/board/BoardViewport.ts`, `frontend/src/lib/components/board/BoardCanvas.svelte` (interaction) on top of `BoardScene.svelte` (the drawing, shared with the GIF export, see 8.12).

## 8.7 Unsaved changes

"Saved" means **saved on the server** whenever a user is logged in, and for every situation saved there (a *server situation*, ch. 8.15); only in **local mode** (not logged in) a situation that isn't on the server counts as saved once it is **exported** (confirmed product decision, roadmap Phase 2 step 5: when logged in, a JSON export of a new, never-saved situation does not count as saved).

- `SituationEditor` keeps a simple dirty flag (`hasUnsavedChanges` store, `isDirty()`): it becomes true with any edit that changes the situation (undo and redo included) and false when a situation is created or loaded/imported/opened, when it is exported as JSON in local mode and isn't a server situation (`markSaved()`, decided by `SituationWorkflow.exportCurrent` with its `isLoggedIn` dependency), or when a save on the server succeeds (`acknowledgeSave`). Exporting while logged in or exporting a server situation does **not** clear it; neither does exporting an animated GIF (8.12). It is deliberately a flag, not a comparison: undoing back to the starting state still counts as unsaved.
- **Something to save** (Save button, Ctrl/Cmd+S; confirmed product decision): a situation never saved on the server always has something to save, also without edits; a server situation only while dirty (`SituationSaver.hasChanges(link, dirty)`). Without something to save the Save button is disabled (its tooltip says "Save (no unsaved changes)") and Ctrl/Cmd+S does nothing except keeping the browser's "Save page" dialog away.
- Starting a new situation (start page, a folder's page or editor), importing a file, opening a saved situation from the start page or a folder's page, or going back to the start page (or the folder's page) with the editor's badge while dirty asks **"Discard changes?"** (Discard / Cancel, reusable `ConfirmDialog`); when logged in or for a server situation the message says "haven't been saved", otherwise (local mode) "haven't been exported". Confirm proceeds, Cancel (or Escape) keeps the current situation. For an import or an opened saved situation the question comes after it was read successfully.
- While dirty, a `beforeunload` handler (`UnsavedChangesGuard`) makes the browser show its own warning when the page is left or reloaded. Other in-app navigation (e.g. the browser's Back button from the editor to the start page) keeps the situation in memory and is not affected.

## 8.9 Frames and the details panel

**Frame operations** (all through `SituationEditor`, none undoable, all refresh `updatedAt` and mark the situation unsaved):

| Operation | Rule |
|---|---|
| Add | Inserts a copy of the **active** frame right after it — same elements with the same element ids, same description, new frame id — and makes the copy active. The copy starts with an empty undo history; the source frame's edit session ends (its history is sealed, its steps stay). From then on the frames are independent: a change in one frame never propagates to another. No limit on the number of frames. |
| Delete | After the confirmation "Delete frame?" (Delete / Cancel, the shared `ConfirmDialog`). The last remaining frame can't be deleted (the button is disabled). If the active frame is deleted, the previous frame becomes active (the next one if it was the first); deleting another frame keeps the active one. The deleted frame's undo history is dropped. The strip's Delete button always deletes the active frame. |
| Reorder | Moves a frame to another position; the active frame stays the same frame (it may get a new number). |
| Switch | Not an undo step; seals the edit session. The edit popover closes and the selection is cleared, because element ids repeat across frames. |

Frame numbers are 1-based positions and change with the order; frames have no names. The file format needs no change for this: frame order and descriptions were already part of format version 2 (8.3).

**Frame strip** (`FrameStrip`): a `<nav aria-label="Frames">` with an ordered list; each frame is a button showing its number and a thumbnail, the active one with `aria-current="step"`. It scrolls horizontally when the frames don't fit and keeps the active frame in view. Actions: Move frame left/right, Add frame, Delete frame.

- **Thumbnails** (`FrameThumbnail`, geometry in `FrameThumbnailGeometry`): a small inline SVG rendering of the field markings and the frame's elements from the model, oriented like the board (full field landscape; half field portrait with its goal at the bottom, via `BoardViewport`). Elements are drawn 2.5× their board size so they stay visible, arrows (below the other elements) with their board styles enlarged the same way; labels are not drawn. SVG (instead of an offscreen Konva stage) keeps thumbnails cheap, crisp at any size, re-rendered reactively when the frame changes, and testable in jsdom.
- **Reorder by drag and drop** (`FrameReorderGesture`, a pure state machine fed by Pointer Events, so it works for mouse, pen, and touch, unlike HTML5 drag and drop): with mouse/pen a drag starts after the pointer moved 8 CSS px (less is a tap, which selects the frame); with touch the finger has to rest for 400 ms first (a long press), so a quick swipe still scrolls the strip. While dragging, the frame follows the pointer, the others make room, and the strip auto-scrolls near its edges; the target position is the number of other frames whose center lies before the dragged frame's center. pointercancel, lost pointer capture, and Escape cancel without reordering; the click that follows a drag doesn't select.
- **Keyboard alternative:** the "Move frame left" / "Move frame right" buttons move the active frame by one position (also usable by touch). Keyboard/swipe frame *switching* is not part of the MVP.

**Details panel** (`SituationDetails`): an `<aside>` named "Details" with the situation's title (`<input>`) and description (`<textarea>`), plus the active frame's description (`FrameDescriptionEditor`, labelled "Frame N description"). Descriptions are edited as Markdown source; nothing is rendered yet. Title and situation description are stored on every input and are not undoable (a blank title is stored as is and shown as the default title of the UI language, also as the field's placeholder); the frame description is one undo step per focus of the field (blur ends the session). Keyboard shortcuts (undo/redo, Delete/Backspace) are ignored while typing in these fields (8.4, 8.5). The header keeps showing the title.

Implementation: `frontend/src/lib/editor/SituationEditor.ts`, `frontend/src/lib/editor/FrameWorkflow.ts` (confirmation, popover/selection reset), `frontend/src/lib/commands/ChangeFrameDescriptionCommand.ts`, `frontend/src/lib/components/frames/`, `frontend/src/lib/components/details/SituationDetails.svelte`.

## 8.10 Arrows

Arrows (`Pass`, `Run`, `Shot`) are elements like players and markers (stable id, per-frame copy, color, undoable edits), but they are drawn from a start to an end point and can be bent. They are free: not attached to players, they don't follow them. They have no label.

**Model** (`ArrowElement`, `ArrowGeometry`): `start`, `end` and an ordered list of **bend points** the curve passes through (none = straight; any number). The curve is a **uniform Catmull-Rom spline** through start → bends → end, converted to one cubic Bézier per segment (the end points are duplicated as phantom neighbours). It passes exactly through every bend, so a dragged bend stays under the finger, it is smooth at every bend, and without bends it is a straight line. `ArrowGeometry` is a pure value class: sampling, end tangent (for the arrowhead), bounds, translate/clamp, insert/move/remove a bend, straighten.

**Rendering** (`ArrowPainter`, pure, used by the board and the frame thumbnails): fixed styles per type in scene units — Pass dashed (width 4), Run wavy (width 4, a sine wave along the curve that fades in and out), Shot thick (width 9) — and the same filled arrowhead for all types (length 26), oriented along the curve's end tangent; the line stops under the head. Arrows are drawn in their own group **below** the point elements (one Konva layer: arrows, point elements, overlay), whatever their position in the frame's element list. Thumbnails draw them as SVG with the same styles, enlarged like the other elements.

**Drawing** (arrow tool active; `ArrowGestures`, a pure state machine owned by `BoardInteractionController`):

| Gesture (arrow tool active) | Effect |
|---|---|
| Press and drag (≥ 6 CSS px), release | Draws an arrow from the press point to the release point; a translucent preview follows the pointer. Also when the press is on a player or another element: players and markers aren't draggable while an arrow tool is active. |
| Tap on the empty field | Sets the **start point** (a marker is shown); clears the selection and closes the popover. |
| With a start point set: tap anywhere (also on an element), or drag and release | Sets the **end point** there and draws the arrow. With a mouse the preview follows the hovering pointer. |
| Tap on an element (no start point set) | Selects it and opens the popover, as with every other tool. |
| Escape, changing the tool, pointercancel, a second finger | Cancels the arrow being drawn (and a set start point). |

A new arrow is black (`ElementCatalog.arrowColor`) and of the active type; the tool stays active and the new arrow is **not** selected. Arrows shorter than 24 CSS px on screen are discarded. Start and end are clamped to the visible area (the field, or the visible half). Drawing an arrow is one undo step.

**Editing a selected arrow** (any tool): the selected arrow shows **handles** — its start, its end, every bend, and a small "+" (**add bend** handle) in the middle of every segment. Handles keep their on-screen size and have 44 CSS px hit circles; the "+" handles lie below the others.

| Gesture | Effect |
|---|---|
| Drag the start, the end or a bend | Moves that point (clamped to the visible area); live preview, one undo step on drop. |
| Drag a "+" | Inserts a new bend there (one undo step "Add bend"). |
| Tap a "+" | Inserts a bend at the middle of that segment. |
| Tap a bend | Makes it the **active bend** (highlighted) and opens the popover, which offers **Remove bend**. |
| Double-tap / double-click a bend | Removes it. |
| Drag the arrow's line | Moves the whole arrow, keeping its shape; it stops where any of its points would leave the visible area. |

The arrow popover ("Edit arrow") offers Type (Pass/Run/Shot only — the type can't change between arrows and point elements), Color (the palette, see below), and under **Bends**: **Edit shape** (closes the popover but keeps the arrow selected, so the handles stay usable — needed on phones, where the bottom sheet can cover the board; Close clears the selection like for every element), **Remove bend** (only with an active bend), **Straighten** (only when bent; removes all bends), and Delete arrow. Adding a bend, removing a bend and straightening are undo steps of their own.

**Colors:** every element's color can be changed in its popover (Player color / Color), from one palette: the four player colors, grey (the initial color of markers and the ball) and black (the initial color of arrows). The point element popover lists only point types, the arrow popover only arrow types.

Implementation: `frontend/src/lib/model/elements/` (`ArrowElement`, `ArrowGeometry`, `ElementType`), `frontend/src/lib/commands/ReshapeArrowCommand.ts`, `frontend/src/lib/board/` (`ArrowGestures`, `ArrowHandle`, `BoardInteractionController`, `Selection` with the active bend), `frontend/src/lib/components/board/` (`ArrowPainter`, `ArrowShape`, `ArrowHandleShape`, `ArrowDraftPreview`, `BoardCanvas`), `frontend/src/lib/components/frames/FrameThumbnailGeometry.ts`.

## 8.11 Playback

The frames of a situation can be played as a **slideshow** in the editor.

**Rules:**

| | |
|---|---|
| Start | Play always starts at **frame 1**, whatever frame is active. Play is disabled (and Space does nothing) with only one frame. |
| Timing | Every frame is shown for the same **frame duration** — one global setting, 1 / 2 / 3 / 5 s, default 2 s. Hard cut between frames (no transition). |
| End | After the last frame playback **stops**, or starts over at frame 1 when **Loop** is on (default off). |
| Stop | Stop (or the natural end) shows the frame that was active **before** playback again. Playback never changes the model or the active frame: the board just shows the slideshow's frame while it runs. |
| Pause | Keeps the shown frame; Play resumes it with the time it had left. |
| Previous / Next | Show the neighbouring frame for its full duration, staying playing or paused; nothing happens before the first or after the last frame (also with Loop on). A tap on a frame in the strip shows that frame the same way. |
| Settings | Frame duration and Loop are **app settings**, not part of the situation file; they are remembered in the browser (`localStorage`, key `tacticalboard.playbackSettings`). If the browser storage is unavailable or holds invalid data, the defaults are used. Changes apply right away, also during playback (a new duration from the next frame on). |

**While playing or paused** the editor is read-only: the board shows the frame without selection, handles or popover and reports no taps, drags or arrow gestures; the tool panel, Undo/Redo (buttons and shortcuts), Delete/Backspace, adding/deleting/reordering frames and the details fields are disabled. Frame descriptions are **not** shown (the frame description field is hidden). Starting playback first ends the edit session, drops an arrow being drawn, clears the selection and closes the popover. New, Load and the badge stay available: when the situation is replaced (new, imported, closed) playback stops. The JSON export works during playback and doesn't stop it; opening the GIF export stops playback first (8.12).

**Controls** (`PlaybackControls`, a region named "Playback" between the board and the frame strip): Play/Pause, Previous frame, Next frame, Stop (all ≥ 44 px), the status "Frame n / N" (the frame on the board), a "Frame duration" select and a Loop toggle button (`aria-pressed`). Below 640 px width (container query) the buttons are icon-only and the status is "n / N"; the texts stay the accessible names. The frame strip marks the frame being shown (`aria-current="step"`).

**Keyboard** (`PlaybackShortcuts`): Space = Play/Pause (also starts playback); ← / → = previous / next frame and Escape = Stop, **only during playback** — outside playback ← / → do nothing (switching frames by keyboard is not part of the MVP) and Escape keeps its board meaning (8.5). Ignored while typing in a text field or select, during IME composition, with Ctrl/Cmd/Alt held, while an element is dragged, and inside modal dialogs. Space on a focused button or link is left to the browser, which activates that control (so it never triggers twice). Swipe gestures and a fullscreen/presentation mode are planned for later.

**Building blocks** (`frontend/src/lib/playback/`, pure; `PlaybackTimeline` is shared with the GIF export, 8.12):

- `PlaybackTimeline`: frames + settings → entries `{ frameId, index, startMs, durationMs }`, `totalMs`, `frameAt(ms)` (a frame covers `[startMs, startMs + durationMs)`; before the start the first frame, from the end on the last one).
- `PlaybackSettings` (immutable value) and `PlaybackSettingsStore` (Svelte store, persisted through a `KeyValueStorage`; `WebKeyValueStorage` wraps `localStorage` and swallows every storage error).
- `SlideshowPlayer`: states `stopped | playing | paused` with the shown index and frame id as a store; `play`/`pause`/`resume`/`toggle`/`stop`/`next`/`previous`/`seek`; reads the timeline and the loop setting from a source whenever it needs them; timers through an injected `Scheduler` (`TimeoutScheduler` in the browser, `FakeScheduler` in tests).
- `PlaybackShortcuts`: the keyboard mapping above.

`frontend/src/lib/editor/PlaybackWorkflow.ts` connects the player to the editor (leave editing before starting, stop when the situation changes); the editor page shows `playing ? the slideshow's frame : the active frame` and passes the read-only state to `BoardCanvas` (`readonly`), `ToolPanel` (`disabled`), `FrameStrip` (`playing`) and `SituationDetails` (`disabled`).

## 8.12 Animation export

The frames of a situation can be exported as an **animated GIF** — the slideshow of 8.11 as a file to send around.

**Rules** (product decisions):

| | |
|---|---|
| Format | GIF only (no video). |
| Content | **All** frames, in order, as they look on the board: field, arrows, point elements, labels. No title, descriptions, frame numbers or watermark are burned in. Elements in the hidden half of a half-field situation are not visible (like on the board). |
| Look | Always the **light** field look (white surface, black lines), also when the app is in the dark theme. |
| Orientation | Full field landscape; half field portrait with its goal at the bottom (like the board; the floorball half is square). |
| Resolution | Selectable preset, given by the long side: **Small 600 px, Medium 1200 px (default), Large 1800 px**; the other side follows the shown field (full floorball field 1200 × 600 at Medium, half field 1200 × 1200). |
| Timing | Every frame is shown for the playback **frame duration** (8.11, shown read-only in the dialog — it *is* the playback setting); hard cuts. The GIF **loops forever**. |
| File | `<slug of the title>.gif`, with the same slug rule as the JSON export (8.3); `situation.gif` when the title has no usable characters. |
| Share | Where the browser can share files (`navigator.canShare({ files })`, typically phones), the dialog additionally offers **Share** (native share sheet). Closing the share sheet is not an error. |
| Saving | Exporting a GIF does **not** count as saved: the unsaved-changes flag (8.7) is untouched. |

**UI:** the header's **Export** button is a disclosure button (`aria-expanded`) with two choices below it, "Situation file (JSON)" and "Animated GIF" (≥ 44 px each; Escape, a press outside or moving focus away closes them). "Animated GIF" opens the modal **Export animated GIF** dialog (native `<dialog>`, `modalDialog` action): Resolution radios (with the pixel size for this situation), Frames and Frame duration as a description list, **Create GIF**. While the GIF is created: a `<progress>` bar ("frame n of N") and **Cancel**; the resolution is locked. Then: **Download** (focused), **Share** where supported, Close. Failures are shown as an alert with "Try again". Escape/Close cancels a running export. Opening the dialog stops a running slideshow, ends the edit session and closes the popover; the export uses the situation as it is at that moment.

**Building blocks** (`frontend/src/lib/export/`):

- `BoardScene.svelte` (`lib/components/board/`): the board's drawing — Konva stage laid out by a `StageFit`, field, arrows group, point elements group with labels, an overlay snippet — with optional `SceneInteraction`. `BoardCanvas` adds interaction and handles on top; the export uses it without interaction. So the GIF is drawn by exactly the same code as the board.
- `FrameRasterizer` (`FrameRendererFactory`): mounts `BoardScene` with Svelte's `mount()` into a hidden, `inert` container outside the viewport, laid out by `BoardViewport.fit` for exactly the export size; per frame: set the elements, `await tick()`, `stage.toCanvas({ pixelRatio: 1 })` (Konva renders each layer separately, so composite operations stay inside their layer as on screen), drawn onto an opaque white ground → RGBA pixels. `dispose()` unmounts and removes the container.
- `ExportResolution`: the presets and `sizeFor(contentSize)` (whole pixels, long side = preset).
- `AnimationEncoder` (interface: `addFrame(rgba, durationMs)`, `finish(): Blob`, `mimeType`, `fileExtension`) with `GifAnimationEncoder`: one GIF frame per slide, delay = frame duration, NETSCAPE loop count 0 (forever); a 256-color palette quantized **per frame** (RGB565, local color tables) — frames are hard cuts, so per-frame palettes keep each frame's colors exact without dithering.
- `SlideshowExporter`: `PlaybackTimeline` (same timing as playback) → rasterizer → encoder; `onProgress(done, total)` (0 … N), cancellation through an `AbortSignal` (rejects with an `AbortError`), yields to the UI (a macrotask) after every frame so progress paints and Cancel stays responsive; the rasterizer is always disposed.
- `AnimationExport` (runes state behind the dialog): phases `idle | rendering | ready | failed`, resolution choice, file naming, Download (`BrowserFileDownloader`) and Share (`WebFileShare`).
- `lib/files/`: `BrowserFileDownloader` (any `Blob`, through an object URL revoked 40 s after the click; also used by the JSON export), `FileNameSlug` (the shared slug rule), `WebFileShare` (feature-detected Web Share API with files).

**Dependency:** [gifenc](https://github.com/mattdesl/gifenc) (MIT, ~9 kB, no dependencies) encodes the GIF. It is loaded with a dynamic `import()` only when a GIF is created, so it is a separate chunk and the editor bundle doesn't grow. It ships no TypeScript types; the used API is declared in `frontend/src/lib/export/gifenc.d.ts`.

**Performance:** rendering and encoding run on the main thread, one frame at a time (in headless Chromium about 0.1–0.3 s for 3 frames, depending on the resolution); see [known limitations](../known-limitations.md).


## 8.13 Login and session (Phase 2)

- The backend is the OIDC client (ADR-006): `GET /auth/login?returnUrl=…` starts the Authorization Code flow with PKCE, `/auth/callback` finishes it, `POST /auth/logout` ends the session (and at the IdP, if it supports it). `returnUrl` must be a local path.
- The session is an `HttpOnly`, `Secure`, `SameSite=Lax` cookie under the app's origin. The IdP tokens stay in the backend.
- **CSRF:** every state-changing request (`POST`, `PUT`, `PATCH`, `DELETE`) needs an antiforgery token header that the frontend gets from the backend; together with `SameSite=Lax` this blocks cross-site requests.
- `GET /api/me` returns the current user, or `401` when not logged in. The frontend then offers "Log in" and keeps working in local mode (ch. 1).
- **Users** are identified by the IdP's issuer + `sub`. The first valid login creates a normal user (just-in-time). The display name comes from the `name` claim (fallbacks: `preferred_username`, then `email`, then "User" — confirmed) on that first login only; afterwards it is changed in the app and never overwritten by the IdP.
- A blocked user gets no session and lands on `/?login=blocked` ("Account blocked."); every other failed login lands on `/?login=failed` ("Login failed.", no reason). An existing session of a blocked or deleted user ends with the next request.
- **Deleted accounts:** the same identity may log in again and then gets a **new, empty account** (new id, display name from the IdP again); the deleted account stays deleted (confirmed product decision).

Implementation (roadmap Phase 2 step 2):

- **Backend, host** (`backend/src/TacticalBoard.Api/Authentication/`): a cookie scheme (the session, default for authenticate and challenge) plus the standard ASP.NET Core OpenID Connect handler, wired in `AuthenticationServiceCollectionExtensions`. Code flow with PKCE (S256), `response_mode=query` (the IdP's redirect back is a top-level GET, so the `SameSite=Lax` correlation and nonce cookies arrive), scopes `openid profile email` (configurable), userinfo endpoint on, claim names unmapped (`sub`, `iss`, `name`, `preferred_username`, `email`). Only standard OIDC is used; nothing is specific to an IdP product.
  - `GET /auth/login?returnUrl=` (`AuthEndpoints`): `ReturnUrlPolicy` keeps only local paths (one leading `/`, no `//`, no backslash, no control characters), anything else becomes `/`. Already logged in: straight to the return URL.
  - `/auth/callback` is the handler's redirect URI. `OidcEvents.TicketReceived` maps the IdP login (`ExternalLoginMapper`) to a local user through `IUserAuthentication` (Users module) and replaces the principal with a session principal holding **only the local user id** (`SessionClaims`, claim `tb_uid`). Of the tokens only the ID token is kept in the (encrypted) cookie, as `id_token_hint` for the logout; access and refresh tokens are dropped, nothing calls the IdP's APIs. A blocked user is redirected to `/?login=blocked` (`AuthPaths.LoginBlockedRedirect`; the start page shows "Account blocked."); an unusable identity and any failure in the callback (e.g. a forged or replayed state) redirect to `/?login=failed` (the start page shows "Login failed." without a reason).
  - The redirect URIs sent to the IdP are built from `App__PublicBaseUrl` (`PublicUrls`); without it, from the request.
  - `POST /auth/logout`: deletes the session cookie and, if the IdP's discovery document has an `end_session_endpoint` (`DiscoveryEndSessionSupport`), continues with RP-initiated logout (`id_token_hint`, `post_logout_redirect_uri` = `/auth/signout-callback`, which returns to `/`). Without one (or if the IdP is unreachable) the logout stays local and redirects to `/`. IdP-initiated (front-channel) logout is switched off.
  - **Session cookie** `tb_session` (`__Host-tb_session` with secure cookies): `HttpOnly`, `SameSite=Lax`, path `/`, `Secure` unless `Session__SecureCookies=false` (local http only). It is a browser-session cookie (no fixed expiry) whose ticket expires after 14 days without use (sliding). It is protected with the data-protection keys, persisted to `DataProtection__KeysDirectory` (a volume), so sessions survive a restart.
  - **Per-request check** (`SessionCookieEvents.ValidatePrincipal`): every request with a session cookie loads the user once by primary key (`IUserAuthentication.ResumeSessionAsync`, a no-tracking projection); a missing, deleted or blocked user makes the cookie invalid at once (cookie deleted, request continues anonymous). The same snapshot backs `ICurrentUser` for the rest of the request, so the system administrator flag is always current.
  - **401 instead of redirects**: endpoints that need a session (`RequireAuthorization()`) answer `401` (`403` for forbidden) as Problem Details (`unauthorized` / `forbidden`); the cookie scheme never redirects to a login page.
  - **CSRF** (`AntiforgeryValidationMiddleware`, after authentication and authorization): every request with a method other than GET, HEAD, OPTIONS, TRACE needs a valid ASP.NET Core antiforgery token, in the header `X-CSRF-TOKEN` (fetch) or the form field `__RequestVerificationToken` (the logout form); otherwise `400` with type `invalid-antiforgery-token`. `GET /api/antiforgery` returns `{ token, headerName, formFieldName }` and sets the HttpOnly, `SameSite=Strict` antiforgery cookie (`tb_antiforgery`). Tokens are bound to the session: a token fetched before the login is not valid after it. A request without a session gets `401` before the token is checked.
- **Backend, Users module** (`backend/src/Modules/TacticalBoard.Users/`): `User` (issuer, subject, display name, system administrator flag, blocked flag, created at, soft delete) in the table `users` with a unique index `ix_users_issuer_subject` on (issuer, subject) **among non-deleted rows** (`deleted_at IS NULL`; migration `AllowNewAccountAfterDeletion`), so an identity has at most one live account and gets a new one after its account was deleted. `UserAuthenticationService` looks up the identity's non-deleted account, creates one just in time otherwise (a parallel first login of the same identity is caught by the unique index and continues with the winner) and rejects blocked users; `DisplayName.FromIdentityProvider` takes the first non-blank of `name`, `preferred_username`, `email` (control characters become spaces, cut to the maximum length), or `User` if none is sent.
- **Display name rules** (`DisplayName`): trimmed, not empty, at most **100 characters** (UTF-16 code units, the same unit as the browser's `maxlength`), no control characters, not unique. The limit is a technical choice (fits every UI place, the column is `varchar(100)`).
- **API**: `GET /api/me` → `{ id, displayName, isSystemAdministrator, preferredLanguage }` or `401` (`preferredLanguage`: the UI language the user chose, a lower-case language tag such as `"de"`, or `null`, ch. 8.18). `PUT /api/me/display-name` with `{ "displayName": "…" }` → the updated user, or `400 validation-failed` with `errors.displayName` / `fieldErrors.displayName` (8.2). `PUT /api/me/language` with `{ "language": "de" }` → the updated user, or `400 validation-failed` with `errors.language` / `fieldErrors.language` (`required`, `unsupported-language`).
- **Preferred language** (`LanguageTag`, Users module): a BCP 47 language tag (primary subtag of 2–3 letters, then subtags of 1–8 letters or digits, separated by `-`), trimmed, stored in lower case, at most 35 characters (column `users.preferred_language`, `varchar(35)`, nullable; migration `AddPreferredLanguage`). The backend checks only the form, not which languages the frontend has (technical decision: a new language needs no backend change). `null` until the user chooses a language.
- **Current user for other modules**: `ICurrentUser` (Users `Contracts`: `IsAuthenticated`, `Id`, `IsSystemAdministrator`), scoped per request. `IUserDirectory` (Users `Contracts`) returns the display names of existing (non-deleted) users for "created/changed by" (one query per list).
- **Frontend**: `ApiClient` (`frontend/src/lib/api/`) is the reusable REST client: same-origin requests, Problem Details as `ApiError`, no backend (network error or a non-API answer such as the dev server's proxy error) as `ApiUnavailableError`, and the antiforgery header on every state-changing request (token fetched once, re-fetched and retried once when rejected). `AuthSession` (`frontend/src/lib/auth/`) holds the session state (`unknown`, `anonymous`, `unavailable`, `authenticated` with the user) as a store, refreshed once when the app starts, and knows the login/logout URLs. The account corner of the shared navbar (`AccountArea` in `AppNavbar`, on the start page and in the editor, 8.8) shows "Log in" (a full page navigation; with "Login failed." / "Account blocked." from `AuthSession.loginNotice`), or the user's menu (`AccountMenu`: "Change display name" with `DisplayNameDialog`, "Log out" as a real form POST with the antiforgery field), or, without a backend, only a muted "Local mode". Local mode is unaffected in every state.

## 8.14 Bootstrapping the first system administrator

The deployment configuration lists identities that are system administrators from the start (`Bootstrap__SystemAdministrators`, entries `issuer|subject`). When such an identity logs in and **no active system administrator exists yet**, or the identity logs in for the very first time, it gets the role. Afterwards the role is managed only in the app, so revoking it there sticks. If every system administrator is gone (e.g. deleted directly in the database), a configured identity gets the role again on its next login — the recovery path.

Implementation: `SystemAdministratorBootstrap` (Users module, applied in `UserAuthenticationService` on every login). "Active" means neither blocked nor deleted. "Logs in for the very first time" means the identity never had an account: a new account after a deleted one (8.13) gets the role only when no active system administrator exists. Entries are read by `BootstrapConfiguration`: one value with entries separated by `;` or line breaks (`Bootstrap__SystemAdministrators`), or a list (`Bootstrap__SystemAdministrators__0`, `__1`, …); the issuer is everything before the first `|` and must equal the IdP's `iss` exactly (e.g. no trailing slash for Keycloak). A malformed entry stops the start. In the local Compose stack the realm user `trainer` (fixed subject) is configured. How an operator finds an identity's issuer and subject is described in [docs/deployment.md](../deployment.md#the-first-system-administrator).

## 8.15 Saving situations on the server (Phase 2)

- **Areas:** a situation lives in exactly one area (a user's personal area or a team) and optionally in one folder of that area. It can be moved between the folders (and the top level) of its area, but not moved or copied to another area (only via JSON export/import).
- **Folders:** flat, names unique within the area (ignoring upper/lower case), at most 64 characters, deletable only when empty; renamed and deleted on the folder's page only. Listed by name (case-insensitive), each with the number of its (non-deleted) situations — no created/changed by for folders (confirmed product decisions).
- **Save:** explicit, with the Save button or Ctrl+S / Cmd+S (no autosave). The first save of a new or imported situation creates it **where it was started**: the area and folder (or top level) from which "New situation" or "Import" was chosen; from the start page, the top level of the personal area (without login: no server save, only export); from the editor's own New / Load, the folder of the situation being edited (top level if it has none or in local mode; confirmed product decision). Later saves update it.
- **Storage:** see ADR-009. Each save writes a new revision; the situation row carries the metadata (title, field type, created/updated at and by, current revision).
- **Titles:** unique among the non-deleted situations of an area, compared after trimming and ignoring upper/lower case. Saving with a title that exists there fails (Problem Details, the editor shows the error). When an imported situation is saved for the first time and its title exists, it gets the suffix " (2)" (or the next free number); a title that already ends with " (n)" is numbered on from n + 1 instead of getting a second suffix (confirmed product decision: a copy of "Powerplay (2)" becomes "Powerplay (3)"). Default titles are incremented within the area: "Untitled Situation", "Untitled Situation (2)", …
- **Conflicts:** optimistic concurrency with the revision number (`ETag` / `If-Match`). If someone else saved in between, the save fails with `412`, and the user chooses **Overwrite** (save again on top of the newest revision), **Save as copy** (a new situation with title suffix " (2)" or the next free number) or **Cancel**.
- **Shown metadata:** created by/at and last changed by/at.
- **Format:** the server always stores the current file format version; the frontend migrates older files on import (ch. 8.3) and the backend validates the document before saving.

Implementation (roadmap Phase 2 step 3: the personal area; step 4: its folders; step 8: team areas — the same rules, endpoints for a team's area, the role matrix):

**Rules and decisions:**

- **Validation:** the document must be valid in the **current** format (8.3; `formatVersion` 3 — older versions are rejected, the frontend migrates before sending). The backend's `SituationDocumentValidator` is a port of the frontend's `SituationFileValidator` with the same rules, paths and messages; **keep both in sync** with every format change (the backend's unit tests run the ported cases and validate the frontend's `__fixtures__` files). Problems come back as `validation-failed` with `errors` keyed `document.<path>` (e.g. `document.situation.frames[0].elements[2].x`). Extra properties are ignored and stored as sent.
- **Server-owned values:** the server is the authority for the situation's `id` (a UUID v7 it generates; the client's id is replaced on the first save), `createdAt` (first save), `updatedAt` (every save; both from the server clock, cut to milliseconds) and the title. On every save it **stamps** these values into the stored document (`SituationDocument.Stamp`), so a revision's document always equals its row's metadata; the client's values are ignored. The columns `sport`, `field_type` and `format_version` are taken from the document; sport and field type can't change after the first save.
- **Titles:** trimmed; a blank title becomes "Untitled Situation" (the server's own default, English); at most **200 characters** (a technical limit, `document.situation.title`). Compared case-insensitively after trimming (`normalized_title`: trimmed, Unicode NFC, upper-cased invariantly), unique among the non-deleted situations of the area — checked in the domain and enforced by the partial unique index `ix_situations_area_title` (`area_kind, area_id, normalized_title` where `deleted_at IS NULL`).
- **Numbered titles** (first save only, decided on the server, `SituationTitle.FirstFree`): `origin: "imported"` or `"copy"` keeps a free title and otherwise gets " (2)" or the next free number. A title that already ends with **" (n)"** (n a positive whole number, after a space) is numbered on its base from **n + 1** upwards instead of getting a second suffix: "Powerplay (2)" → "Powerplay (3)" (or the next free number after it; numbering always counts upward from the highest number, gaps such as a free "Powerplay (2)" are not filled) — confirmed product decision. `origin: "new"` with the **default title** gets the next free number the same way ("Untitled Situation (2)", …). The server knows its own default title "Untitled Situation" (any case, or blank); the default titles of the UI languages ("Unbenannte Situation", …) it doesn't know, so the client flags them with **`titleIsDefault: true`** in the request (technical decision, ch. 8.18; the backend stays language-agnostic). Any other taken title on a new situation, and every taken title on a later save (also the default title), is `409 duplicate-title`. If a parallel save takes the chosen number first, the server chooses again (up to three attempts).
- **Revisions and concurrency:** every save writes a new row in `situation_revisions` (`jsonb`, primary key situation + number) and updates the situation row; the revision number is the `ETag`. A save names the revision it is based on (`If-Match`); if it is no longer the current one → `412`. Two parallel saves of the same revision can't both win: the situation's `current_revision` is an EF Core concurrency token and the revision's primary key is unique; the loser gets `412`. **Overwrite** = the client saves again with `If-Match` = `currentRevision` from the `412`; **Save as copy** = `POST` with `origin: "copy"` (a new situation in the same area, numbered title).
- **Access:** Situations and Folders ask Areas (`IAreaAccess`). A situation or folder in an area the user can't read is `404` (no hint that it exists); one they can read but not change is `403 forbidden` (team Readers). The personal area: only its owner (system administrators included, 8.1). A team's area: every member reads, Admins and Editors write (`TeamAreaAccessRule` → `ITeamAuthorization`, 8.1). The lists of a team's area (`/api/teams/{team}/…`) answer a non-member `403 forbidden` instead of `404`, because the team itself (name, logo) is visible to every logged-in user and only its content is not — the same answer as the team's member list (8.17).
- **`canWrite` on every folder and situation** (technical decision): whether the current user may change it, computed per request from `IAreaAccess.CanWriteAsync` of its area (once per list). The UI only offers what is allowed; the server checks every request again.
- **Team areas (technical decisions, roadmap Phase 2 step 8):** the endpoints are generalized by area **only where an area is named** — the lists and first saves at an area's top level and the folder lists and creation: `/api/personal-area/…` (the current user's) and `/api/teams/{team}/…` (a team's). Everything addressed by a folder's or situation's id (`/api/folders/{id}…`, `/api/situations/{id}…`) is area-agnostic: the server knows the item's area. Resolving `{team}` is Areas' job (`IAreaDirectory.TeamAreaAsync` through Teams' `ITeamDirectory`), so Folders and Situations stay without a reference to Teams (ch. 5.2). Titles, default-title numbering and folder names are unique per team area exactly as per personal area (the same indexes on `area_kind, area_id`); no migration was needed.
- **No moving or copying between areas** (ch. 1): a move names only a folder; a folder of another area (personal ↔ team, or another team) is `404 folder-not-found`. "Save as copy" creates the copy in the original's area (and folder). Copying works only through JSON export and import.
- **Created/changed by:** user ids in the row; the display names come from Users (`IUserDirectory`, through Areas' `IActorDirectory`) when the situations are read, so a renamed user shows the new name and a deleted user `null` ("Deleted user" in the UI).
- **Delete:** soft delete (8.16) of the situation; its revisions stay. No `If-Match` (deleting is not blocked by a newer revision). The title is free again.
- **Folders:** flat, in an area (`area_kind`, `area_id` like situations; personal areas and, from roadmap step 8, teams through the same `IAreaAccess`). **Names:** trimmed, not empty, at most **64 characters** (confirmed product decision that 100 is more than needed; 64 chosen as the technical limit, `varchar(64)`, migration `LimitFolderNameLength`, which stops the start if a stored name is longer — only possible in databases from the time the limit was 100, rename such folders first; longer names are `400 validation-failed` with the field code `too-long` and `maxLength: 64`), no control characters; unique among the non-deleted folders of the area, compared like titles (`UniqueNames.Normalize`: trimmed, Unicode NFC, upper-cased invariantly) — checked in the service and enforced by the partial unique index `ix_folders_area_name` (`area_kind, area_id, normalized_name` where `deleted_at IS NULL`). A taken name is always an error (no numbering, unlike titles). Renaming has no concurrency check (the last rename wins). Access as for situations: a folder in an unreadable area is `404`, writing needs write access (`403`).
- **Situations in folders:** `folder_id` is the folder in the situation's area or `null` (top level); it is checked through Folders' `IFolderDirectory` (exists, not deleted, same area) — there is no database foreign key across the module boundary. **Titles stay unique in the whole area**, not per folder: a title taken in another folder or at the top level counts (and numbering looks at the whole area).
- **Moving is a metadata change, not a save** (technical decision; confirmed product decision that a move doesn't count as a change): it changes only `folder_id`. It writes **no revision**, so the revision number and the `ETag` stay, and an editor that has the situation open can keep saving on its revision without a conflict; it needs **no `If-Match`** and never conflicts with a content save (the move writes only the folder column, bypassing the revision check). "Last changed by/at" stays (it describes the content), so a move doesn't reorder the lists. The stored document has no folder, so no revision would differ anyway.
- **Delete only when empty, also under parallel requests:** deleting a folder, moving a situation into a folder and a first save in a folder each run in one database transaction (`IUnitOfWork`) that locks the folder row — `FOR UPDATE` for the deletion, `FOR SHARE` for placing a situation — so the emptiness check can't miss a situation placed meanwhile (runtime: ch. 6.4, ADR-012).
- **Situation count per folder** (confirmed product decision): the folder list carries the number of non-deleted situations per folder. Folders may not use Situations (ch. 5.2), so it asks through its own contract `IFolderContents.CountSituationsByFolderAsync(area)`, which Situations implements with one grouped query (`SELECT folder_id, count(*) … WHERE <area> AND folder_id IS NOT NULL AND deleted_at IS NULL GROUP BY folder_id`); `FolderService.ListAsync` joins the counts to the folders in memory (a folder missing from the counts has 0). Two queries per list, independent of the number of folders (technical decision: keeps the module boundary instead of one SQL join across both modules' tables). Only the list has the count; the count is as of loading the list (not live).
- **Save as copy** (after a conflict) creates the copy in the same folder (or top level) as the original, as the editor last knew it (confirmed product decision).
- **Started in the editor** (confirmed product decision): the editor's own New and Load (import) save into the folder of the situation being edited — a server situation's folder (as last known, also after a move on another page) or the folder an unsaved one was started in; the top level if it has none, and in local mode. An unsaved situation started in a folder counts as "in that folder" for New/Load and the badge (confirmed product decision; implemented in `SituationLink.placeOf` / `EditorPlace`).

**Backend structure:**

- **Areas** (`backend/src/Modules/TacticalBoard.Areas/`): `Contracts`: `AreaReference` (kind + owner id; `AreaReference.Personal(userId)`), `AreaKind` (`Personal`, `Team`), `IAreaAccess` (`CurrentUsersPersonalArea()`, `CanReadAsync`, `CanWriteAsync`), `IAreaDirectory` (`TeamAreaAsync(teamKey)`) + `TeamAreaNotFoundException` (`team-not-found`), `AreaResponse` (`{ kind, id }`), `IActorDirectory` (current user id, display names), `IAreaContentDeletion`. `Application`: `AreaAccess` dispatches to one `IAreaAccessRule` per kind (a kind without a rule is denied); `PersonalAreaAccessRule` = owner only; `TeamAreaAccessRule` = `ITeamAuthorization.CanReadContentAsync` / `CanWriteContentAsync` (roadmap step 8); `AreaDirectory` (through Teams' `ITeamDirectory`); `TeamAreaDeletion`.

- **Situations** (`backend/src/Modules/TacticalBoard.Situations/`): `Domain`: `Situation` (metadata, `Create`/`Revise`/`MoveTo`), `SituationRevision`, `SituationTitle`, `SituationDocument` + `SituationDocumentValidator`, the domain errors (`SituationErrors.cs`). `Application`: `SituationService` (list top level / folder, get, create at the top level / in a folder, update, move, delete), `SituationFolderContents` (`IFolderContents`), `SituationAreaContentDeletion` (`IAreaContentDeletion`: bulk soft delete of an area's situations; revisions stay), `ISituationRepository` (`SaveFolderAsync` writes only the folder; `CountByFolderAsync` the grouped count), `SituationOrigin`. `Infrastructure`: `EfSituationRepository`, the table configurations (`situations`, `situation_revisions`). `Endpoints`: `SituationEndpoints`, `RevisionTag` (ETag ↔ revision). Migrations `AddSituations`, `AddFolders`.
- **Shared:** `IUnitOfWork` (SharedKernel) / `EfUnitOfWork` (Infrastructure): one transaction on the request's context; nested use joins the running transaction; a failing `SaveChanges` inside it rolls back only to EF Core's automatic savepoint, so the numbered-title retry still works inside a transaction. `UniqueNames` (SharedKernel) is the one comparison form for titles and folder names.

**Frontend structure** (`frontend/src/lib/storage/`, components in `frontend/src/lib/components/storage/`):

- `Area` (`PERSONAL_AREA`, `teamArea(id)`, `areaOf` the server's `{ kind, id }`). `SituationApi` (the REST calls; `list`/`create` take a `SaveTarget`: an area's top level — `/api/personal-area/situations` or `/api/teams/{id}/situations` — or a folder; `move`), `FolderApi` (folders; `list(area)` / `create(area, name)`), `SituationSerializer.toDocument` / `fromDocument` (the file format as the server's document).
- `SaveTarget` (`{ area, folderId }`; `TOP_LEVEL`, `inFolder(id, area?)`, `teamTopLevel(teamId)`): where a situation was started. `SituationWorkflow.createNew` / `importFile` take it (default: top level) and pass it to the link; `StartActions.svelte` (New situation + Import, used by the start page and the folder's page — there in its own section, or in the empty state of an empty folder) and `SituationDialogs` hand it through. The editor's own New and Load get it from `EditorPlace` (`frontend/src/lib/editor/`): a value derived from the link (`SituationLink.placeOf`: a server situation's folder, or an unsaved one's target) and the login state; it also gives the badge's target (`home()`: the folder's page, the team's page, or `/`). For a situation the user may only view, `startTarget()` is the personal top level.
- `SituationLink` (singleton `situationLink`; `writable()`: an unsaved situation, or a server situation with `canWrite`): whether the editor's situation is unsaved (`origin` new / imported, and `target`: where its first save goes) or a server situation (its last known metadata and revision). `SituationWorkflow` sets it on New, Import and leaving; export marks only a non-server situation as saved (8.7). A move on the start page or a folder's page updates the folder of the editor's server situation (`relocate`), keeping its revision.
- **Read-only editor** (roadmap step 8): for a server situation with `canWrite: false` (a team Reader) the editor page blocks editing like during playback (8.11) — board without selection or gestures, tool panel, Undo/Redo and their shortcuts, Delete, frame add/delete/reorder (`FrameStrip readonly`), title and descriptions (`FrameDescriptionEditor readonly`) — hides Save (Ctrl/Cmd+S does nothing) and shows the note "View only: you're a Reader in this team…" in the details panel. Playback, switching frames, the JSON and GIF export, New, Load and the badge stay available.
- `SituationSaver`: Save button and Ctrl/Cmd+S (`SaveShortcut`; in text fields too, never inside a modal dialog; without login the browser keeps its own Ctrl+S). Only with something to save (8.7: never saved, or dirty); otherwise the button is disabled and saving does nothing. First save → `POST` to the link's target (top level or folder) with the link's origin, plus `titleIsDefault: true` for a new situation whose title is the default title of any UI language (`DefaultTitles`, 8.18); later saves → `PUT` with `If-Match`; Save as copy → `POST` into the original's folder (or top level). ## 8.16 Soft delete

- Situations, folders, teams, memberships, join requests and users are never deleted physically: they get a `deletedAt` timestamp and disappear from all queries. There is no restore UI and no final purge yet. (Implemented for all of them; account deletion follows with roadmap step 10. A team logo is not an item: replacing or removing it overwrites or removes its row; a deleted team keeps its logo row, reachable only through the team — technical decision, so a later restore gets it back.) A member who leaves or is removed gets a soft-deleted membership; joining again creates a new one. Decided join requests (accepted, rejected) stay as history.
- Deleting a team soft-deletes its folders, situations, memberships and pending join requests — implemented in roadmap step 7 in one transaction with the team row locked (`TeamDeletionService`, ch. 8.17); the folders and situations through the contract chain `ITeamDeletionParticipant` (Teams) → `TeamAreaDeletion` (Areas) → `IAreaContentDeletion` (implemented by Folders and Situations in step 8: `FolderAreaContentDeletion` and `SituationAreaContentDeletion`, ADR-015). Bulk soft deletes inside it (`ExecuteUpdate`) set `deleted_at` from `IClock` themselves — the team, its memberships, folders and situations get the same timestamp; a team folder that still contains situations goes too (the whole area goes away), the situations' revisions stay. A folder can be deleted only while it contains no (non-deleted) situations (implemented: `FolderService.DeleteAsync` asks Situations through `IFolderContents` inside one transaction with the folder locked, ch. 8.15). A soft-deleted situation still points at its folder; it doesn't count, so the folder can be deleted.
- Uniqueness (situation titles and folder names per area, team names) only counts non-deleted items, so names can be reused.
- A deleted user's identity may log in again and gets a new, empty account (8.13): the unique index on the identity also counts non-deleted users only.
- **Account deletion** (by the user or a system administrator): blocked while the user is the last Admin of a team with other members. Otherwise their personal area (folders, situations), memberships and pending join requests are soft-deleted, teams where they were the only member are deleted, and the user record is anonymized (display name removed) and soft-deleted. "Created/changed by" on team situations then shows "Deleted user".
- Implementation (plumbing): an entity implements `ISoftDeletable` (or derives from `SoftDeletableEntity`, SharedKernel). `TacticalBoardDbContext` gives every such root entity type the named global query filter `SoftDelete` (`deleted_at IS NULL`); queries that need deleted rows use `IgnoreQueryFilters(["SoftDelete"])`. `SoftDeleteInterceptor` turns a `Remove` of such an entity into an update that sets `deleted_at` from `IClock`, so it is never deleted physically. Cascading a delete to dependents (e.g. a team's folders) stays an explicit domain operation. Code: `backend/src/TacticalBoard.Infrastructure/Persistence/`.

## 8.17 Teams (Phase 2)

- **Name:** unique among non-deleted teams, compared after trimming and ignoring upper/lower case. **Logo:** optional; PNG, JPEG or WebP; the backend scales it down to fit 256 × 256 px, re-encodes it (dropping metadata) and stores it in the database.
- **Code:** 6 characters from A–Z and 0–9, generated randomly when the team is created (retried on a collision), never changed. The team link contains the code. **Only members get a team's code** (confirmed product decision, roadmap step 7): non-members see name and logo only.
- **Overview:** only for logged-in users; lists all teams with name and logo, searchable by name or code (a team found by its code still shows only name and logo to a non-member).
- **Join requests:** one pending request per user and team; it can't be withdrawn; after a rejection the user may send a new one. Joining through a link also creates a request. Accepted users become Readers.
- **Members:** every member sees the member list (Admins first, then Editors, then Readers, each by name — confirmed product decision); Admins change roles (their own included; giving themselves a lower role asks first — confirmed product decision) and remove members (other Admins too); every member may leave; the team always keeps at least one Admin. Admins delete the team.
- **Content:** a team's situations and folders (ch. 8.1, 8.15; roadmap step 8): members see them on the team's page, Admins and Editors change them.

Implementation (roadmap Phase 2 step 6: teams, overview, team page, logo; step 7: join requests, members and roles, leaving, deleting teams, code only for members; step 8: team situations and folders, self-demotion question, member order by role):

**REST API** (all need a session, otherwise `401`; `POST`/`PUT`/`DELETE` also the antiforgery header, 8.13; errors as Problem Details with stable codes, 8.2). `{team}` is the team's **code** (matched ignoring case) **or its id** (a UUID) — the server takes both (`TeamKey`), because a non-member has no code: the overview links them, and logo URLs point, by the id. Anything else is `404 team-not-found`.

**Rules and decisions:**

- **Name** (`TeamName`): trimmed, not empty, at most **64 characters** (technical limit, like folder names; `varchar(64)`), no control characters. Unique among non-deleted teams, compared through `UniqueNames.Normalize` (trimmed, NFC, upper-cased invariantly) — checked in the service and enforced by the partial unique index `ix_teams_name` (`normalized_name` where `deleted_at IS NULL`), so parallel creations with the same name end with one team and `409` for the others. A deleted team's name is free again.
- **Code** (`TeamCode`): six characters from A–Z and 0–9 (36⁶ ≈ 2.2 billion), drawn by `RandomTeamCodeGenerator` with a cryptographically secure random number generator (injected as `ITeamCodeGenerator`), so codes can't be guessed from earlier ones. A code is unique among **all** teams, deleted ones included (unique index `ix_teams_code`, not partial; technical decision: a link never leads to another team later). The service skips a taken code and, if a parallel creation took it between the check and the insert (the index rejects it), retries with a new code — at most 10 attempts, then `500`.
- **Code only for members** (confirmed product decision): `TeamService` fills `code` in the team view, the overview items and `GET /api/me/teams` only for teams the current user is a member of; logo URLs use the id. A non-member who opens the team's link knows the code from the URL anyway; the page still doesn't show it or the link. **Team keys** (`TeamKey`, technical decision): every `{team}` route takes the code or the id, so the overview can link a non-member to `/teams/<id>`.
- **Membership** (`TeamMembership`, table `team_memberships`): team, user, role (`Admin`, `Editor`, `Reader`, stored as text), joined at, soft delete; at most one non-deleted membership per team and user (partial unique index `ix_team_memberships_team_user`). Creating a team adds its creator's Admin membership in the same `SaveChanges` (one transaction). Accepting a join request adds a Reader membership (`ForAcceptedRequest`). Leaving and removal soft-delete the membership; joining again creates a new one.
- **Join requests** (`TeamJoinRequest`, table `team_join_requests`, migration `AddMembership`): team, user, requested at, status (`Pending`, `Accepted`, `Rejected`, as text), decided at/by, soft delete. At most one pending request per team and user: partial unique index `ix_team_join_requests_pending` (`team_id, user_id` where `status = 'Pending' AND deleted_at IS NULL`); decided requests stay as history, so a new request after a rejection is allowed. Accepting or rejecting is allowed only once (the domain refuses a second decision; the service answers `404 join-request-not-found`). The requester learns about a rejection only from the team's page (the request is no longer pending, "Ask to join" is offered again; open question in the [roadmap](../roadmap.md)).
- **At least one Admin** (`TeamRoster`, domain): built from the team's current memberships, it changes a role or takes a member out only if another Admin remains (`LastTeamAdminException` → `409 last-team-admin`). It holds **under parallel requests** because every change of a team's members, join requests or existence runs in **one transaction that first locks the team row** (`TeamLocks`, `ITeamRepository.LockAsync`: `SELECT … FROM teams WHERE … AND deleted_at IS NULL FOR UPDATE`, PostgreSQL syntax kept in the repository, ADR-002, ADR-012): such changes of one team run one after another, and each reads the memberships only after getting the lock (runtime: ch. 6.7). The rights are checked after the lock too (`ITeamAuthorization` reads the role fresh), so an Admin demoted meanwhile is refused. The same lock serializes deciding a request (two Admins deciding at once: one wins, the other gets `404`), sending a request (the unique index is the backstop), and deleting the team (a request or change waiting for the lock then finds no team: `404`). The integration tests run these races with parallel requests (and fail without the lock).
- **Authorization** (`ITeamAuthorization`, Teams `Contracts`, ch. 5.2), backed by the permission matrix `TeamPermissions` (domain, ch. 8.1): `RoleOfCurrentUserAsync(teamId)` (the role in a non-deleted team, or `null`), `CanChangeDetailsAsync` (name and logo: Admins), `CanSeeMembersAsync` (members), `CanManageMembersAsync` (roles, removing: Admins), `CanDecideJoinRequestsAsync` (Admins), `CanDeleteTeamAsync` (Admins), `CanReadContentAsync` (members) and `CanWriteContentAsync` (Admins and Editors) for the team's situations and folders (step 8, used by Areas' `TeamAreaAccessRule`). Every answer is read from the database per request, so a removed, demoted or leaving member loses access with their next request. System administrators get their team-management rights here with roadmap step 9 (confirmed: they may also rename a team and change its logo); content rights never come from the system administrator flag, only from a membership. `ITeamDirectory` (`TeamDirectory`) finds a non-deleted team's id by its key for Areas.
- **Deleting a team** (`TeamDeletionService`): Admins only; in the locked transaction it calls every registered `ITeamDeletionParticipant` with `TeamDeletion(teamId, deletedAt, deletedBy)` (Areas' `TeamAreaDeletion` passes it on to every `IAreaContentDeletion` for the area `(Team, id)`: Folders and Situations soft-delete the team's folders and situations), then soft-deletes the pending join requests and all memberships (bulk `ExecuteUpdate`) and the team. A failing participant rolls everything back. The name is free again; the code stays taken; the logo row stays with the deleted team. The frontend asks "Delete team?" first and then opens the start page.
- **Logo upload** (technical limits): the upload may be at most **5 MiB** (`LogoUpload.MaxBytes`; shown as "5 MB") and at most **25 megapixels** (checked from the image header before decoding, against decompression bombs). The format is detected from the content, never from the file name or the declared type: **PNG, JPEG, WebP**; SVG, GIF, anything else or an unreadable file is `unsupported-image`. The endpoints limit the request body to 5 MiB + 64 KiB (`RequestSizeLimit`, multipart limit); a larger request is cut off by the server with `413 payload-too-large` before it is read (behind Kestrel; the in-process test server doesn't enforce it, there the app's own `file-too-large` check answers). The frontend checks type and size before uploading, so users normally see its message.
- **Logo processing** (`ILogoImageProcessor`, implemented with SkiaSharp in `SkiaLogoImageProcessor`, ADR-014): decode (JPEG and WebP at a reduced scale where the decoder supports it, at least twice the target size), turn upright by the EXIF orientation, scale down to fit **256 × 256 px** keeping the aspect ratio (never up; mipmapped linear filtering), convert to sRGB, and encode a fresh **PNG** (keeps transparency). Nothing of the upload's metadata survives (EXIF, text chunks, ICC profiles). Animated images keep their first frame.
- **Logo storage**: the PNG bytes in the table `team_logos` (one row per team, primary key `team_id`, `bytea`, content type, hash, updated at/by), apart from `teams`, so lists never load image bytes; `teams.logo_hash` says whether there is a logo and versions its URL. The hash is the first 128 bits of the PNG's SHA-256 (hex). Setting a logo writes the row with an upsert (`INSERT … ON CONFLICT DO UPDATE`, PostgreSQL syntax kept in the repository, ADR-002) and the team's hash in one transaction (`IUnitOfWork`); parallel uploads end with the last one. Removing deletes the row — at once, without a confirmation (confirmed product decision).
- **Rename** has no concurrency check (the last rename wins), like folders.

**Backend structure** (`backend/src/Modules/TacticalBoard.Teams/`): `Contracts`: `ITeamAuthorization`, `TeamRole`, `ITeamDeletionParticipant` + `TeamDeletion`. `Domain`: `Team` (create, rename, logo hash, delete), `TeamMembership` (`ForCreator`, `ForAcceptedRequest`, `ChangeRole`), `TeamJoinRequest` + `JoinRequestStatus`, `TeamRoster` (the at-least-one-Admin rule), `TeamPermissions` + `TeamPermission` (the matrix), `TeamKey`, `TeamName`, `TeamCode`, `TeamLogoImage` (a processed logo with its hash), `TeamLogo` (the stored row), the domain errors (`TeamErrors.cs`). `Application`: `TeamService` (search, mine, get, create with code retries, rename, set/remove/get logo), `TeamMembershipService` (list, change role, remove, leave), `TeamJoinRequestService` (send, list pending, accept, reject), `TeamDeletionService`, `TeamLocks` (the locked transaction), `TeamMemberNames` (display names through Users' `IUserDirectory`, member order), `TeamAuthorization`, `TeamSearch` (query validation), `LogoUpload` (limits and field errors) with `ILogoImageProcessor`, `ITeamCodeGenerator`, `ITeamRepository` / `ITeamMembershipRepository` / `ITeamJoinRequestRepository`, the views. `Infrastructure`: `EfTeamRepository`, `EfTeamMembershipRepository`, `EfTeamJoinRequestRepository`, `TeamUniqueIndexes` (unique-index violations → repository exceptions), the table configurations, `RandomTeamCodeGenerator`, `SkiaLogoImageProcessor`. `Endpoints`: `TeamEndpoints`, `TeamMemberEndpoints` (members and join requests), `TeamResponses.cs`. Migrations `AddTeams` (`teams`, `team_memberships`, `team_logos`) and `AddMembership` (`team_join_requests`). The form endpoints opt out of the framework's own form antiforgery check (`DisableAntiforgery`), because the app's `AntiforgeryValidationMiddleware` checks every state-changing request already (8.13). ## 8.18 Localization (Phase 2)

Confirmed product decisions (roadmap Phase 2 step 5, ch. 1 *Languages*): the UI is German and English, English is the fallback, and another language needs only a new translation file. Only **system texts** are translated; **user content** (titles, descriptions, folder names, position labels, display names) never is. The language starts as the browser's; a switcher in the navbar changes it; it is remembered in the browser and, when logged in, in the account, whose language wins on login. Server errors are worded by the frontend from stable codes.

**Approach** (ADR-013): a small, class-based i18n of our own with **typed message catalogs**, no library.

- **Catalogs** (`frontend/src/lib/i18n/locales/`): one TypeScript file per language, `export default { code, name, messages }`. `en.ts` is the reference: the type `Messages` is derived from its `messages`, and every other catalog is declared `Messages`, so a missing, extra or misspelled key, or a text with the wrong parameters, fails `pnpm run check`. Texts with values are functions (`deleteMessage: (title) => …`), so each language orders and inflects them itself — including **plural forms** of counts (`folders.situationCount(n)`: "1 situation" / "2 situations", "1 Situation" / "2 Situationen"; a language with more plural categories would use `Intl.PluralRules` in its own function); numbers are formatted per language (German decimal comma, thousands separators). A test compares the catalogs' shapes key by key.
- **Registry** (`LocaleRegistry`): collects every file in `locales/` with Vite's `import.meta.glob` — adding `fr.ts` adds French to the registry, the switcher and the browser detection, nothing else changes. It resolves a language tag by its primary subtag (`de-CH` → `de`) and matches the browser's preferences (`navigator.languages`, most preferred first): the first language the app has, otherwise English. With German and English that is "de\* → German, otherwise English", also when e.g. `fr-CH, de-CH` is preferred (the first *supported* preference wins; technical decision).
- **State** (`I18n`, singleton `i18n` in `$lib/i18n`): the stores `language` and `messages`; components render `{$t.common.cancel}` (`t` = `i18n.messages`), so a switch re-renders every text at once. `start(preferences)` runs in the root layout before the first render: a remembered choice (`localStorage` key `tacticalboard.language`, read and written through `WebKeyValueStorage`, every storage failure ignored) wins over the browser's language. `select(code)` switches and remembers. Every change sets `<html lang>`.
- **Texts from classes** (`Translatable = (messages) => string`, `Messages.ts`): classes that produce user-facing texts (the save, folder and list flows, confirmation questions, form validation) return a function of the catalog instead of a string; components call it with the current catalog. So a text already on screen follows a language switch, and classes stay testable without the UI (`inEnglishDeep` in `lib/testing/i18n.ts`). The **debug notification log** (dev builds only) stays English (`inEnglish`).
- **Account** (`AccountLanguage`, singleton `accountLanguage`): attached in the root layout, it follows `AuthSession`: when a user is logged in (on login, or when the app starts with a session), the account's `preferredLanguage` is applied if the app has that language — once per login, so a later choice in the same session isn't overridden. An account without a language keeps the browser's, and nothing is written to the account until the user actively picks a language in the switcher (confirmed product decision). `choose(code)` (the switcher) applies the language, remembers it in the browser and, when logged in, stores it with `PUT /api/me/language` (`AuthSession.changeLanguage`); a failure to store it leaves the language in the browser and is only logged.
- **Server errors** (`ProblemText`): no server → "server not reachable", `401` → "session ended", a `validation-failed` problem → its `fieldErrors` codes, each worded as "<field> <problem>" (e.g. "Der Name darf nicht leer sein."), any other problem → the catalog's text for its code (`messages.problems`), unknown codes → the caller's fallback or the generic "Something went wrong". The server's English `title`/`detail` are never shown (8.2). Technical details may stay English inside a localized message — the reason of a failed GIF export or share (from the browser or encoder) and the field paths of server validation messages (e.g. `document.situation.title`) — confirmed product decision.
- **Dates** in the lists and the details panel are formatted with `Intl.DateTimeFormat` in the UI language (e.g. "Oct 4, 2026, 10:30 AM" / "04.10.2026, 10:30").
- **Element types, colors, positions** (`ElementCatalog`, `PositionCatalog`) carry only keys (type, color id, position code); their names come from the catalog (`messages.elements`, `messages.colors`, `messages.positions[sport][code]`). The position *codes* (C, LV, …) are stored labels and are not translated; the English UI names them in English now (e.g. "LV (Left defender)"), the German UI as before.
- **Tests** run in English: `vitest-setup.ts` resets the language after every test (`i18n.reset()`, remembered choice removed); tests that check German select it explicitly.

**Default titles across languages** (confirmed product decision): a new situation created with a blank title stores the default title **of the UI language at that moment** as its real title ("Untitled Situation" / "Unbenannte Situation"; `NewSituationForm.toInput(defaultTitle)`). It is user content from then on and is not translated later. A blank title (e.g. from a file) is shown as the default title of the current language. For the server's numbering the frontend sends `titleIsDefault: true` with the first save of a new situation whose title equals the default title of **any** bundled language (`DefaultTitles`, ignoring case and surrounding spaces), so "Unbenannte Situation" is numbered like "Untitled Situation" (8.15). The server's own fallback for a blank title stays "Untitled Situation".
